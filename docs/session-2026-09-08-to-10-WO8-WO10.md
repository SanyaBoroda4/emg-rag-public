## 0. Project background (what already existed on 2026-09-08)

**EMG** is a countertop fabrication company in Charleston, SC. The project is a
retrieval-augmented question-answering system over its business data:

- **Moraware** (job tracking): 5,569 jobs, 44,495 activities (Quote,
  Measure, Template, Install, Removal, Repair, Tile, …), 12,201 forms.
- **QuickBooks**: 5,257 invoices.
- Data lives in Postgres + pgvector on a small Hetzner server (2 GB RAM,
  shared with live WhatsApp/MCP production containers — never touched).
  The database is a **frozen snapshot as of 2026-07-30**.

Pipeline: raw JSON → Postgres → derived views (`v_*`) → chunked/embedded
notes → hybrid retrieval (BM25 + dense + Voyage rerank) + a text-to-SQL lane
+ a Haiku router (structured / semantic / hybrid / refuse) → grounded
answers → an evaluation harness with a golden question set.

Key mechanics:
- Models: router Haiku 4.5 (temperature 0 since WO8), text-to-SQL Haiku
  4.5, answer Haiku 4.5, eval judge Sonnet 5 (always a different model from
  the generator). Embeddings voyage-3.5-lite, reranker Voyage rerank-2.5-lite.
- The text-to-SQL lane may only read whitelisted `v_*` views through a
  read-only Postgres role (`rag_reader`), validated by sqlglot.
- **Canonical business definitions are implemented once as a Postgres
  view**, exposed to the SQL lane as authoritative, and gated by a script
  that asserts hand-verified cases. Before WO8 this existed for pipeline
  status / quote conversion (`v_job_pipeline_status`,
  `v_quote_conversion_monthly`, `sql/012`–`013`).
- Migrations are append-only (`sql/001` … never edited after landing).
- Golden set (`evals/golden_set.csv`): questions with expected answers,
  route, and status `verified` / `draft` / `FAILING`. Eval tiers: 1 routing
  accuracy, 2 retrieval recall, 3 LLM-judged generation (correctness by a
  numeric scorer for structured questions, by the judge otherwise;
  faithfulness always by the judge).
- **Prior baseline (Aug 14, 63 questions):** routing 95.2%, generation
  63.5% (40/63), faithfulness 91.7%.

Repos: private `github.com/SanyaBoroda4/emg-rag`; a sanitized public mirror
`emg-rag-public` is re-synced after every push (`scripts/sync_public.sh`).
Server auto-pulls the private repo every minute. Evals run on the server.

## 1. WO8 — Wasted-template detection (`v_wasted_templates`)

### 1.1 The business question

How often does the template person drive to a job that is not ready, and
which project manager (the job's `salesperson`) let it happen? Every wasted
template is an extra trip and a readiness failure by the PM. Alex's stance:
always eliminate template trips — better to wait a few days and template
everything at once.

### 1.2 The rule (as implemented in `sql/014_wasted_templates.sql`)

Alex judged 10 real jobs by hand; the rule was reverse-engineered from those
verdicts and must reproduce all 10. A naive "2 templates + 1 install =
wasted" heuristic was wrong on 4 of 10, which is why the rule has this shape.

- **Step 0 — real events only.** A Template or Install counts only if
  `status_name IN ('Complete','Paid in Full and Finished')` and it has a
  date. Undated `Estimate` placeholders never count (job 680 has two
  template rows, only one real → not flagged). *(Widened in WO9, see §2.)*
- **Step 1 — phases.** A job's real templates are walked in date order; a
  gap of more than `PHASE_GAP_DAYS = 30` starts a new phase. Jobs 1422 and
  1681 (two templates far apart) are "two phases of the job", neither
  wasted; job 772's 2023 window-seal template is a separate phase from its
  2020 pair.
- **Step 2 — structural signal.** Within a phase, every template except the
  last is *structurally wasted* if no real Install falls strictly between
  it and the next template. Job 3117 (Template → Install → Template →
  Install) is the critical negative: zero wasted. Jobs 852 and 1084 (two
  templates, no install between) → first template wasted.
- **Step 3 — note signal.** A template is *note-wasted* if readiness-failure
  language matches its own note, or a Measure note **on the same day**
  (Measure + Template is one visit and the note often sits on the Measure
  row, e.g. job 478 "Measure + Template"). Patterns are a curated,
  case-insensitive regex list in the view's `params` CTE (`readiness_re`):
  not ready / weren't ready / wasn't ready; cabinets not installed / not
  ready / not set; cabinets need(ed) adjusting / redo / fix; redo … cabinets;
  sink not installed / not on site; uninstalled; could not / can't / didn't /
  unable to template; before I could template; will be installed later.
  **Redo phrases** (`retemplate`, `template … again`, `redo of template`,
  `second trip`, `2nd trip`, `wasn't ready last time`, `first trip`,
  `finish templating`) are written on the *redo* trip, so they flag the
  **previous** template of the same phase, never the one they sit on, and a
  note carrying a redo phrase is never used as readiness evidence against
  its own template. A redo phrase on the first template of a phase flags
  nothing (the earlier template is a separate phase).
- **Step 4 — verdict.** `wasted = structural_wasted OR note_wasted`;
  `wasted_reason` ∈ `structural` / `note` / `both` / NULL. No "partial"
  category (job 478 counts as wasted).

Two interpretation choices had to be made against the literal WO text and
were reported rather than hidden:

1. Read literally, the note rule flags the template the phrase is written
   on — that would have counted the productive redo trips on 852 and 5491 as
   *second* wasted templates. Hence the previous-template attribution.
2. "Measure note within the same phase window" was narrowed to *same day*:
   21 Measure notes match the readiness regex, but the 15 dated days or weeks
   before the template describe a Measure visit that found the site not
   ready — the later template is the trip that *worked*, so attributing
   those would flag good templates. The 6 same-day ones are real failed
   visits (jobs 560, 1277, 1298, 1964, 2676, 3714).

The WO's pattern list also missed Alex's own examples: 478 ("uninstalled
vanity") and 4743 ("client needed to redo some cabinets before i could
template") matched none of the listed phrases; both patterns were added.

### 2.5 Change 3 — crew questions Q64–73 (1/10 → 10/10)

Alex's Q64–73 ask per-crew job counts, visit counts, per-job and per-visit
square footage for H1 2026. Three causes of failure, three fixes:

- **3a denominator.** The keys divide total sq ft by *all* installed jobs
  (area-less jobs count as 0); the lane's `AVG(total_sq_ft)` skipped the
  NULL of the one area-less job (84.4 vs the correct 83.6). Decision: keys
  are authoritative. Prompt now mandates `SUM(COALESCE(sq_ft,0)) / COUNT(*)`
  over the DISTINCT-job subquery, never `AVG()`.
- **3b per-visit pattern.** The lane had no way to compute sq ft per install
  visit. The WO's formula "SUM(job_sqft) / COUNT(install_activity_id)", read
  literally as a join of `v_job_sqft` onto visit rows, is *itself* the
  double count (125.9 instead of 58.6 for Ihor/Tolik). Final pattern, one
  query, returns everything:

  ```sql
  WITH v AS (SELECT job_id FROM v_activities
             WHERE type_name = 'Install' AND happened AND <crew/date filters>),
       j AS (SELECT SUM(COALESCE(s.total_sq_ft, 0)) AS total_sq_ft, COUNT(*) AS jobs
             FROM (SELECT DISTINCT job_id FROM v) d LEFT JOIN v_job_sqft s USING (job_id)),
       c AS (SELECT COUNT(*) AS visits, COUNT(*) - COUNT(DISTINCT job_id) AS repeat_visits FROM v)
  SELECT j.jobs, c.visits, c.repeat_visits, j.total_sq_ft,
         ROUND(j.total_sq_ft / j.jobs, 1)   AS sq_ft_per_job,
         ROUND(j.total_sq_ft / c.visits, 1) AS sq_ft_per_visit
  FROM j, c
  ```
  plus a grouped variant for "compare / which crew / rank" (GROUP BY
  assignees in both CTEs, joined on assignees). Rule promoted to the top
  Rules list: any question naming a crew uses this pattern and the answerer
  reports every number in the row. Canonical example: a job of 88.5 sq ft
  over 2 visits = 88.5 per job, 44.25 per visit.
- **3c Q73 replaced.** The original example job 5874 has installs dated
  Aug 31 / Sep 2 2026, after the snapshot. New Q73: job 5637 (Rolina – 6222
  N Hwy 17, Yuri/Petro) — 102 sq ft, 2 install visits (May 22, Jun 2 2026)
  → 102 per job, 51.0 per visit. Dates kept out of the key because the
  all-numbers scorer would demand them.

It took four crew-subset runs (Q64–73, then Q34–37 + Q64–73; ≈$0.12–0.18
each) and two full runs to get there, because each fix exposed the next:
first per-visit pattern double-counted; then Haiku returned bare job counts
for "how many jobs did X install"; then the answerer dropped the sq ft even
though the SQL had it; then the multi-crew CTE had an invalid alias scope.
Q36/Q37 (older WO7-era draft crew rows) carried the old AVG-based keys
(107.4, 84.4) and were re-keyed to 104.4 / 83.6.
